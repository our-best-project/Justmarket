# 關鍵決策

每條三件事：**決定了什麼／為什麼／什麼會推翻它**。沒有第三項的不算決策，只是現況。

---

## 1. 用 `articles.status` 當管線交接棒，不引入佇列

**決定**　五段管線靠一個狀態欄位串接：`pending → vectorized → clustered → summarized → scored`。
每段只吃上一格，做完推進下一格。

**為什麼**　MVP 規模下，佇列要付的營運成本（多一個服務、多一種故障模式、多一套監控）
換不到對應的好處；而狀態在 DB 裡帶來的可重跑性是免費的。

**什麼會推翻它**　需要同一段並行多個 worker 搶工作的時候。狀態欄位沒有租約機制，
兩個 worker 會處理到同一批。屆時要的是 `SELECT … FOR UPDATE SKIP LOCKED` 或真正的佇列。

---

## 2. 聚類用 Agglomerative(average) + 日期/ticker 雙閘門

**決定**　cos 距離 < 0.35 的 average linkage，外加日期窗與 ticker 交集兩道閘門。
HDBSCAN 留作對照組。

**為什麼**　實測 F1 0.914 勝過對照組。純語意相似會把「同主題不同事件」併在一起
（例如兩週前後的兩次法說會），雙閘門擋的就是這個。

**什麼會推翻它**　語料規模或來源結構改變（例如加入大量國際新聞）後重跑黃金集，
F1 掉到對照組以下。評測方法與數據見 `src/eventsignal/clustering/REPORT.md`。

---

## 3. `related_tickers` 只掃標題，不掃內文

**決定**　抽取事件關聯個股時只看標題。

**為什麼**　`related_tickers` 的語意是「這個事件**關於**誰」，不是「內文**提到**誰」。
實測 4486 篇：掃標題+內文有 13.3% 的文章被標超過 4 家、單篇最多 58 家，
查台積電會回傳一堆只是內文提到它的新聞；只掃標題後雜訊降到 0.1%、單篇最多 5 家。
代價是涵蓋率從 91.2% 降到 66.3% —— 用 25pp 涵蓋率換掉 99% 雜訊。

**什麼會推翻它**　換成真正的 NER／實體連結模型，能在內文裡分辨「關於」與「提到」。
那時涵蓋率與精確度可以同時要。

---

## 4. 重要性與市場驗證是兩個獨立分數

**決定**　★1–5 的重要性（五維加權：來源廣度 25／權威 20／影響 25／類型 15／新穎 15）
與 0–100 的市場驗證（法人 ±25、股價 ±20、量當放大係數，含一致性閘門與 D0→D+5 狀態機）
分開計算、分開顯示。

**為什麼**　「這件事重要」與「市場買不買單」是兩個問題。合成一個分數之後就再也拆不出
理由，而「每個分數都要能拆解」是這個產品唯一的鐵律。

**什麼會推翻它**　使用者實際只看排序、從不展開理由。那時單一分數確實比較省事。

---

## 5. API 只讀，所有運算在處理層

**決定**　`/api/v1` 全部是 GET，不做任何計算，只把處理層算好的欄位讀出來。

**為什麼**　分數要可重現。同一個事件在不同時間、不同請求下必須是同一個數字，
否則使用者無法信任，也無法討論。順帶讓 API 可以無狀態橫向擴充。

**什麼會推翻它**　出現真正需要即時計算的功能（例如使用者自訂權重的即時重排）。

---

## 6. 前端取不到資料就報錯，不退回 mock

**決定**　資料源失敗時整頁顯示錯誤，不以模擬值替代。

**為什麼**　早期版本會靜默退回 mock，實測後果是：畫面顯示三週前的假數字、資料狀態燈
全亮「真實」、頁尾還宣稱「無模擬內容」—— 使用者沒有任何辦法分辨。一個講市場資料的
產品，寧可什麼都不顯示，也不能顯示分不出真假的數字。

**什麼會推翻它**　沒有。這是產品誠實性的底線，不是技術取捨。

---

## 7. Spider Forge 與正式管線之間是手動邊界

**決定**　AI 生成的爬蟲產出「spider + 內部 CI 認證」，由人決定要不要搬進 `crawler/`。
`spider_forge` 不在任何 Prefect flow 內，也不 import `news_crawler`
（由 `src/spider_forge/tests/test_architecture.py` 守著）。

**為什麼**　自動接上等於讓模型直接改 production 爬蟲。生成品質再高，錯誤模式也是
「看起來對但抓錯欄位」這種安靜的錯 —— 那會污染 articles，而下游全部吃它。

**什麼會推翻它**　生成結果有可靠的自動驗收（跟 golden fixture 逐欄位比對且長期零漂移），
且爬蟲失效的偵測與回滾是自動的。

---

## 8. 三個容器，一份依賴來源

**決定**　`api` / `worker` / `spider-forge` 三個映像檔，依賴全部來自根目錄
`pyproject.toml` 的 extras 與同一份 `uv.lock`。

**為什麼**　之前有四份 requirements 檔（本機一份、Docker 兩份、spider forge 一份），
加套件要四處同步，結果是「本機能跑、容器起不來」。單一鎖檔讓這種漂移不可能發生。
分 extras 則是為了不讓 API 映像檔背 torch。

**什麼會推翻它**　三者需要衝突的版本（例如 spider_forge 要 scrapy 3.x 而 crawler 還在 2.x）。
單一 lock 解不開衝突，那時才該拆成 uv workspace 的獨立成員。

---

## 9. DB 連線一律顯式設 `timezone=Asia/Taipei`

**決定**　`get_conn()` 與連線池都帶 `options="-c timezone=Asia/Taipei"`。

**為什麼**　Neon 預設 session timezone 是 GMT。`CURRENT_DATE` 在台北 00:00–08:00 之間會
慢一天，「今日事件」在那 8 小時內查錯日。這種 bug 只在半夜出現，最難發現。

**什麼會推翻它**　系統要服務多時區使用者。那時日期邊界應該由呼叫端明確指定，
而不是靠連線層的預設值。

---

## 10. 目錄重構不改行為

**決定**　2026-08 把 `workspace/backend/app/<人名>` 的結構攤平成 `src/eventsignal/<職責>`，
過程中只改檔案位置、import 路徑與註解，不改任何執行語意。

**為什麼**　重構與行為修改混在同一次變更裡，出事時分不清是哪一邊造成的。
連 lint 規則也照這條走：需要動到執行語意的規則（ClassVar 標註、zip strict、str-Enum 換基底）
在 `pyproject.toml` 標了 `EXCEPTION` 暫關，而不是順手改掉。

**什麼會推翻它**　沒有。這條是流程紀律。那些暫關的 lint 規則各自開一次變更修完後，
逐條從 ignore 清單刪掉。
